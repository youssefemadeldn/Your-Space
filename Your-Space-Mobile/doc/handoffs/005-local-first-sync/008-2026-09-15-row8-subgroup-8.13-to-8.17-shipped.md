## Bugs Found

None found or fixed this session — 8.14 through 8.17 landed exactly as planned/verified, no
deviations, no regressions. (Prior sessions found and fixed real bugs — see handoff 007 for the
`SyncService` DI list-registration bug fixed in 7.3 — but this session's four sub-steps were all

One **flagged, out-of-scope, not-yet-fixed** finding from 8.17: `dotnet ef database update`
against this environment's local dev Postgres fails on the **already-merged**
`AddPersonSyncVersion` migration (from a much earlier row, not touched this session) —
`setval('People_SyncVersion_seq', 0)` throws because Postgres sequences are 1-indexed and this
from-scratch local DB's `People` table is empty, so the migration's
`COALESCE(MAX(SyncVersion), 0)` backfill produces an invalid 0. This blocks verifying the full
migration chain end-to-end against a real database in this environment, but it is **not**
something 8.17 introduced and was correctly left unfixed per minimal-safe-change discipline —
`dotnet build`/`dotnet test` (342/342 green) remained the verification bar instead, matching the
"local DB may not be reachable/clean" posture already taken back at row 8.5. **If a future
session needs to actually run `dotnet ef database update` against a fresh local Postgres
instance, this will block it** — the fix would be changing every `AddXSyncVersion` migration's
backfill SQL to guard against an empty table (e.g. `WHERE EXISTS (SELECT 1 FROM "X")` around the
`setval` call, or seeding `MockDataSeeder`/`ReferenceDataSeeder` data before running the
migration). Not fixed here — flag it to the user again if it resurfaces.
