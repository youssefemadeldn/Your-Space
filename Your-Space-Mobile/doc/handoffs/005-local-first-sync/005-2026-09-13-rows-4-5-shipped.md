  a pending offline edit's `isDirty` flag.
- `PersonRepositoryImpl.refreshPersons()` now calls `applyPersonsSnapshot` instead of the old
  plain-upsert `savePersons`.

  thin wrapper over `PersonRepository.refreshPersons()`, `@LazySingleton(as: CollectionPuller)`.

  outbox) on connectivity regained, cold start, and app resume, plus a 15-minute foreground

  successful pull only (a failed pull leaves the watermark untouched — no pull backoff, unlike

**Row 5 — Backend delta-sync support for Person (`Your-Space-Backend`):**
- `Person.SyncVersion` (new `bigint` column) — a monotonic cursor backed by a new Postgres
  sequence `People_SyncVersion_seq`. `Person.UpdatedAt` already existed but is plain wall-clock
  `DateTime`, which the design doc explicitly calls insufficient (§6: two same-millisecond
  writes must not be ambiguous to a cursor pull).
- **Bump strategy (user chose this explicitly over a DB trigger via AskUserQuestion):**
  app-level `ISyncVersionProvider`/`SyncVersionProvider` (new, in
  `YourSpace.Repository/Sync/`) — calls Postgres `nextval()` via `SqlQueryRaw`, and
  `PersonService.CreateAsync`/`UpdateAsync`/`DeleteAsync` explicitly assign it before saving
  (a bigserial-style column only auto-populates on INSERT, never UPDATE).
- New `PersonWithSpecs(ownerUserId, since, pageSize)` overload — deliberately **no**
  `DeletedAt == null` filter (tombstones must be included), ordered by `SyncVersion` ascending.
  New composite index `People(OwnerUserId, SyncVersion)` backs it (added via `PersonConfiguration`
  Fluent API + regenerated migration, following this codebase's own precedent of declaring
  indexes in Fluent config rather than hand-writing `CreateIndex` calls that would drift from
  the EF model snapshot).
- New `PersonChangesDto` (`Upserts`, `TombstoneIds`, `Cursor`, `HasMore`) and
  `PersonService.GetChangesAsync(ownerUserId, since, pageSize)` — splits the page by
  `DeletedAt`, batch-resolves reciprocity/photo URLs only for upserts (Rule 11, no N+1),
  `cursor = rows.Any() ? rows.Max(SyncVersion) : since`, `hasMore = rows.Count == pageSize`,
  rejects a negative `since` via a guard clause (`ServiceResult.Fail` + new `ErrorCode`
  `"Person.Since.Invalid"`, new resx entries in both `SharedResource.en.resx`/`.ar.resx`).
- New `PersonsController` endpoint: `GET /api/v1/Persons/changes?since=&pageSize=` (default
  `pageSize=200`, clamped server-side to `MaxChangesPageSize = 500`).
- Migration `20260912211959_AddPersonSyncVersion` — regenerated (not hand-written from scratch)
  after adding the Fluent index, to keep the model snapshot in sync; hand-added the sequence
  `CREATE`/backfill/`setval` raw SQL around the auto-generated `AddColumn`/`CreateIndex` calls.
  Backfill uses `ROW_NUMBER() OVER (ORDER BY CreatedAt, Id)` so existing rows get a real
  increasing version, not all `0`.
- `MockDataSeeder.SeedPersonsAsync` (inserts directly via `DbContext`, bypassing
  `PersonService`) now also assigns `SyncVersion` via the same provider, threaded through as a
  new parameter from `Program.cs`'s `IsDevelopment()` seeding block — otherwise every seeded
  Person row would collide at the column default `0`.
- **Test-infra fix discovered mid-session:** the SQLite-backed `TestWebApplicationFactory`
  can't run Postgres's `nextval()` — the first integration test run failed with a 500. Fixed by
  adding `FakeSyncVersionProvider` (in-memory `ConcurrentDictionary<string,long>` counter, in
  `Common/Fakes/`) and swapping it in inside `TestWebApplicationFactory.ConfigureServices`,
  mirroring the existing `IEmailSender`/`IR2StorageService` fake-swap pattern already there.

## Notes

- **Git workflow the user corrected earlier in this overall feature** (from the prior handoff,
  still in force): the user wants an actual two-parent `git merge --no-ff` per row — feature
  branch → commit → merge into `production` → push — never linear commits directly on
  `production`. This was followed exactly for both row 4 and row 5 this session.
- **Repo-is-monorepo discovery:** this session confirmed (via merge-commit path prefixes) that
  `Your-Space-Mobile` and `Your-Space-Backend` share one `.git` at the `Your-Space` root — a
  fact not previously stated explicitly in either handoff. `git status`/`log`/branch state is
  shared repo-wide; running git commands from inside either subfolder operates on the same
  `production` branch and history. This matters for row 6+: mobile-only rows and
  backend-only rows both land as commits on the *same* branch, interleaved by session, not on
  separate per-project branches.
- **`sync_service_test.dart` observer-leak fix:** row 4 made `SyncService` a
  `WidgetsBindingObserver`. Without cleanup, every test constructing a `SyncService` would leak
  an observer into `WidgetsBinding.instance` that outlives the test, corrupting later
  lifecycle-driven tests. Fixed via a `createService()` test helper that calls
  `addTearDown(service.dispose)` — **any future test file that constructs `SyncService` directly
  needs the same treatment**, not just `sync_service_test.dart`.
- **EF migration regeneration, not hand-authored, for the composite index:** initially hand-wrote
  `migrationBuilder.CreateIndex(...)` directly in the migration without a matching
  `PersonConfiguration.HasIndex(...)` Fluent declaration — this would have left the EF model
  snapshot out of sync with the actually-applied schema (a latent `PendingModelChangesWarning`
  risk). Fixed by removing the migration (`dotnet ef migrations remove`), adding the Fluent
  index declaration first, then regenerating (`dotnet ef migrations add`) so the auto-generated
  `AddColumn`/`CreateIndex` calls come from the model diff, and only the sequence
  `CREATE`/backfill/`setval` raw SQL was hand-added around them. **Apply this same
  remove-then-regenerate discipline for any future migration that needs both a Fluent-declared
  schema element and hand-written raw SQL** — never hand-write an index/column that the Fluent
  model doesn't also declare.
- **Backend integration tests run against SQLite, not Postgres** (`TestWebApplicationFactory`,
  `EnsureCreated()` off the current EF model — migrations, including this row's raw
  `CREATE SEQUENCE`/`nextval` SQL, never execute in that test host at all). This is why the
  Postgres-only `SyncVersionProvider` needed a fake swapped in for tests, and it's a
  reusable data point for row 9's `EventGuest`/`PersonRelationship`/`PersonImage` soft-delete
  decision if that also ends up needing Postgres-specific SQL.
- `feature/row-3-people-outbox` branch mentioned in the prior handoff as "still exists locally,
  unpushed" — not touched or investigated this session; still just flagged as informational.
