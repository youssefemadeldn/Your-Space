## 1. Project Overview

### What Your Space actually is

Based solely on the entities and services implemented, Your Space is a **personal relationship / gift-giving and event-invitation planner** — a private CRM for someone's own social circle, not a multi-tenant social network. A logged-in user:

- Maintains **Groups** (e.g. "Family", "Coworkers") and **People** (contacts) assigned to a group — `Your-Space-Backend/YourSpace.Data/Entities/Group.cs`, `Person.cs`.
- Creates **Events** (e.g. a wedding, a birthday) — `Your-Space-Backend/YourSpace.Data/Entities/Event.cs`.
- Builds a **guest list** per event by adding individual People or a whole Group, then tracks each guest through a status lifecycle (`NotInvited` → `Invited` / `Skipped`, revertible) and records how they were invited (`WhatsApp`, `PhoneCall`, `Physical`) — `Your-Space-Backend/YourSpace.Data/Entities/EventGuest.cs`, `Your-Space-Backend/YourSpace.Data/Enums/EventGuestStatus.cs`, `InviteMethod.cs`.
- Logs **reciprocity history** per person — whether that person has invited *the user* to one of their own past occasions, and how — independent of the user's own events (`Your-Space-Backend/YourSpace.Data/Entities/PersonOccasionHistory.cs:6-8`). `EventGuestsController` exposes a `reciprocity-suggestions` endpoint that appears to use this history to suggest who to invite back; the toggle for this is a per-user `UserSettings.ReciprocitySuggestionsEnabled` flag, off by default (`Your-Space-Backend/YourSpace.Data/Entities/UserSettings.cs:8-10`).

The mobile app (`Your-Space-Mobile/`) is the intended client for this backend, but as of this writing it has **no feature code at all** — see Section 3.

Strong-password rule (`PasswordValidationRules.cs`, shared by Register/ChangePassword/ResetPassword): `MinimumLength(8)`, at least one uppercase, one lowercase, one digit, one non-alphanumeric character. This is enforced **twice** — once by FluentValidation on the DTO, once again by ASP.NET Identity's own password options (`options.Password.RequiredLength = 8; RequireNonAlphanumeric = true;` in `IdentityServiceExtension.cs:16-17`) — redundant but consistent (Identity doesn't check uppercase/lowercase/digit explicitly, so FluentValidation is the stricter gate in practice).

#### JWT flow

- **Issuer:** `"YourSpace"` · **Audience:** `"YourSpaceClients"` (`appsettings.json:6-7`, both overridable)
- **Signing:** HMAC-SHA256 with a symmetric key from `Jwt:Key` — **empty in every committed `appsettings*.json`**; the app throws `InvalidOperationException("Jwt:Key is not configured...")` at startup if it isn't supplied via `dotnet user-secrets` or an environment variable (`Your-Space-Backend/YourSpace.WebAPI/Extensions/IdentityServiceExtension.cs:25-26`, `TokenService.cs:15-16`).
- **Access token expiration:** 15 minutes by default (`Jwt:AccessTokenExpirationMinutes`, `appsettings.json:9`), read per-call in `TokenService.GenerateAccessToken` (`TokenService.cs:17`).
- **Access token claims:** `sub` (user id), `jti` (random guid), `ClaimTypes.NameIdentifier` (user id — this is what `AuthController.GetUserId()` reads), `ClaimTypes.Email`, `ClaimTypes.GivenName`, `ClaimTypes.Surname`, one `ClaimTypes.Role` claim per role (`TokenService.cs:20-29`).
- **Refresh token:** 64 cryptographically-random bytes, base64-encoded, returned to the client raw (`TokenService.GenerateRefreshToken`, `TokenService.cs:45`). **Only the SHA-256 hash is stored server-side** (`RefreshTokens.TokenHash`, unique-indexed) — the raw value never touches the database.
- **Refresh token expiration:** 7 days by default (`Jwt:RefreshTokenExpirationDays`, `appsettings.json:10`).
- **Rotation:** every successful `/refresh-token` call revokes the presented token (`RevokedAt`, `RevokedByIp` set) and issues a brand-new one, linked via `ReplacedByTokenHash` (`AuthService.cs:192-217`).
- **Reuse detection:** if a token that was already rotated away (`ReplacedByTokenHash is not null`) is presented again, the service treats it as a stolen/replayed token and revokes **every** active refresh token for that user, forcing a full re-login (`AuthService.cs:163-179`, error code `Auth.RefreshToken.Reused`). A plain logout-revoked token (no `ReplacedByTokenHash`) does *not* trigger this — it just returns `Auth.RefreshToken.Revoked`.
- **Lockout:** 5 failed password attempts locks the account for 15 minutes (`IdentityServiceExtension.cs:18-19`) — independent of OTP lockout below.

#### OTP mechanics (email confirmation + password reset)

Shared logic in `Your-Space-Backend/YourSpace.Services/Services/OtpService/OtpService.cs`, backed by two near-identical tables (`EmailConfirmationCodes`, `PasswordResetCodes`) via a shared `IOtpCode` interface.

- 6-digit numeric code (`OtpConstants.CodeLength = 6`), expires after 10 minutes (`OtpConstants.ExpiryMinutes = 10`), max 5 wrong attempts before the code locks out (`OtpConstants.MaxAttempts = 5`) — all in `OtpConstants.cs`.
- Generating a new code marks any previous active code for that user as consumed first (`OtpService.cs:61-65`) — only one active code per user per purpose at a time.
- Codes are looked up by `(UserId, ConsumedAt == null)`, **never by the code's hash** — a 6-digit code's hash space is too small to be collision-safe as a lookup key, unlike the high-entropy refresh token (comment at `OtpService.cs:99-102`, and `EmailConfirmationCodeConfiguration.cs:15-16`). The presented code is compared via `CryptographicOperations.FixedTimeEquals` only after narrowing to that one active row.

#### Error response shape

Every response — success or failure — is the same envelope (`Your-Space-Backend/YourSpace.Services/Helper/ServiceResult.cs`), serialized camelCase:

```json
{
  "success": false,
  "message": "Invalid email or password.",
  "errorCode": "Auth.InvalidCredentials",
  "statusCode": 401,
  "timestamp": "2026-07-27T12:34:56.789Z",
  "errors": null
}
```
(`ServiceResult<T>` additionally carries a `"data"` field, null on failure.)

`errorCode` is a **stable, non-localized** string the client is meant to branch on (never `message`, which changes with `Accept-Language`/copy edits) — e.g. `Auth.Register.EmailExists`, `Auth.InvalidCredentials`, `Auth.AccountLocked`, `Auth.EmailNotConfirmed`, `Auth.RefreshToken.{Invalid,Reused,Revoked,Expired,NotFound}`, `Auth.ConfirmEmail.{InvalidRequest,Failed}`, `Auth.ResetPassword.InvalidRequest`, `Otp.{Expired,LockedOut,Invalid}` — full list in `AuthService.cs:27-45`.

Two distinct paths produce this envelope:
1. **FluentValidation failures** (malformed DTO) → HTTP **422**, `errors` populated as `{ "FieldName": ["message1", ...] }`, via a custom `InvalidModelStateResponseFactory` in `Program.cs:29-38` (this exists specifically so FluentValidation failures use the same envelope instead of ASP.NET's default `ProblemDetails` shape).
2. **Guard-clause failures inside `AuthService`** (wrong password, locked account, expired token, ...) → the specific `ServiceResult` factory (`Fail`/`NotFound`/`Conflict`/...) with its own status code, listed in the table above.

Unhandled exceptions never reach Auth in normal operation — `ExceptionMiddleware.cs` is the fallback for anything that escapes a service (500 in Production with a generic message, full exception detail only in Development — `ExceptionMiddleware.cs:27-31`).

- All 10 Auth endpoints listed in Section 2a are implemented, validated, tested (unit + integration), and rate-limited.
- The exact response envelope (`{ success, message, errorCode, data, statusCode, timestamp, errors }`) is already what the mobile app's `unwrapServiceResult`/`ApiManager._extractErrorCode` code expects — confirmed by reading both sides: `Your-Space-Backend/YourSpace.Services/Helper/ServiceResult.cs` vs `Your-Space-Mobile/lib/core/network/api_envelope.dart` and `api_manager.dart:119-131`. Field names line up (`AuthResponseDto.AccessToken`/`RefreshToken` → mobile's `_performRefresh` reads `tokens['accessToken']`/`tokens['refreshToken']`, `auth_interceptor.dart:104-105`).
- `AuthInterceptor`'s refresh-token flow already targets `POST /auth/refresh-token` with `{ "refreshToken": ... }` (`ApiConstants.refreshToken = '/auth/refresh-token'`, `api_constants.dart:20`) — this matches the backend's actual route and `RefreshTokenRequestDto` shape exactly.
- A working Development login (`seed.active@yourspace.dev` / `Seed!Pass123`) already exists for manual end-to-end testing without needing SMTP configured.
- `ApiConstants` already points `dev` at `http://10.0.2.2:5145/api/v1` (Android-emulator-to-localhost alias) and `prod` at a real deployed URL (`api_constants.dart:6-8`) — not placeholder values, so the mobile app is pre-wired to reach a real backend once screens exist.

### Missing on the mobile side to make Auth work end-to-end

1. **`lib/features/auth/` feature module entirely** — data/domain/presentation layers, per the mobile project's own scaffold rules. Nothing exists yet.
2. **Request/response models** — `RegisterRequest`, `LoginRequest`, `RefreshTokenRequest`, `ConfirmEmailRequest`, `ForgotPasswordRequest`, `ResetPasswordRequest`, `ChangePasswordRequest` (`toJson()` only) and `AuthResponse`/`UserProfileResponse` (`fromJson()` + `toEntity()`), matching the backend DTOs field-for-field documented in Section 2a.
3. **`AuthRemoteDataSourceImpl`** calling `ApiManager` for all 10 endpoints.
4. **Domain layer** — `User`/`AuthTokens` entities, `AuthRepository` abstract contract, and only if warranted by the project's own Rule 4 (shared across 2+ cubits or non-trivial logic) any use cases.
5. **Cubits** — per the project's action/query split rule, likely a `RegisterCubit`, `LoginCubit`, and probably a dedicated `OtpCubit`/`PasswordResetCubit` for the confirm-email/forgot-password/reset-password flows, since those are a distinct multi-step flow from plain login.
6. **Screens** — login, register, confirm-email (OTP entry), forgot-password, reset-password, change-password — none exist. `AppRoutes` already has name constants for `login`/`register`/`home` but no `GoRoute` entries and no args classes for the OTP/reset flows.
7. **Wiring the login success path to `SecureStorageHelper.saveToken`/`saveRefreshToken`** — `AuthInterceptor` already *reads* tokens for outgoing requests and *writes* new ones on silent refresh, but nothing yet writes the *initial* pair after a successful login/register response.
8. **`errorCode` branching UI** — the mobile project's own conventions call for switching on `errorCode` (e.g. `Auth.EmailNotConfirmed` → navigate to the OTP screen) rather than matching `message` text (see `Your-Space-Mobile/CLAUDE.md` "Preferring `errorCode` over `statusCode`"). None of this exists yet since no screen consumes an Auth error.
9. **Translation keys** for every string the new screens will need (`en.json`/`ar.json` are currently empty).
10. **A route guard / splash-screen bootstrap check** — deciding whether a stored token exists on app start and routing to `home` vs `login` accordingly. Nothing in `AppRouter` currently does this (`initialLocation` is hardcoded to `splash`, and there's no splash screen either).

## 5. Open Questions / Risks

- **Root `CLAUDE.md` is out of sync with the actual repo layout.** It documents the backend at `.net/` and the mobile app at `flutter/` (`d:\Programing\Your-Space\CLAUDE.md`, "Projects" table), but the real folders are `Your-Space-Backend/` and `Your-Space-Mobile/`. Anyone relying on that table to navigate the repo, or any tooling that reads it, will look in the wrong place. This should be corrected before it causes confusion in a session that hasn't already discovered the real paths.
- **The mobile project's rule files are templated from a different, unrelated project and were never fully adapted.** `Your-Space-Mobile/CLAUDE.md` and `.claude/rules/flutter_feature_prompt.md` repeatedly reference a package named `booksplatform` (e.g. `import 'package:booksplatform/core/network/failure_messages.dart' as core;`) and use a book-domain example (`BookRepository`, `getBook`, `AddReviewDto`) throughout. The actual Flutter package is named `your_space_mobile` (`pubspec.yaml:1`). If these rule files are followed literally for import paths, they will not compile — someone needs to either genericize them or do a find-and-replace before the first feature is scaffolded from them.
- **Database migration now runs unconditionally on every boot, including Production — contradicting both the backend's own documented policy and its own CLAUDE.md rule.** `Your-Space-Backend/doc/handoffs/SETUP.md:30` states "`Production` never migrates on boot — always run `dotnet ef database update`... as an explicit, reviewed deploy step", and the backend's own `CLAUDE.md` (Architecture rule, edge case 9 in `dotnet_scaffold_prompt.md`) says the same. But the current `Program.cs` (`Your-Space-Backend/YourSpace.WebAPI/Program.cs:99-105`) calls `await migrationDbContext.Database.MigrateAsync()` **unconditionally, before the `IsDevelopment()` check** — it is no longer gated at all. This looks like a regression from the recent commit "Add automatic database migration on application startup with logging" (`662ab91`). Worth a deliberate decision: either re-gate it behind `IsDevelopment()` to match the documented policy, or update `SETUP.md`/`CLAUDE.md` to reflect that auto-migrate-on-boot is now intentional for every environment (which carries the concurrent-instance-race risk the backend's own rules warn about).
- **`test/widget_test.dart` in the mobile app is stale and would fail if run** — it still tests the default Flutter counter template against an app that no longer has a counter. `flutter test` is presumably not part of anyone's current workflow yet, or this would already have been caught.
- **Email deliverability for the OTP flow (confirm-email, forgot-password) cannot be verified by reading the code alone.** The implementation is complete and tested, but `appsettings*.json` ships with empty SMTP credentials by design (per the backend's own secrets policy) — whether real values are set via `dotnet user-secrets` locally or environment variables in any deployed environment is outside what this repo inspection can confirm. Whoever builds the mobile confirm-email/forgot-password screens should verify against a real environment before assuming users will actually receive the emails.
- **No endpoint currently uses the `AdminOnly`/`SuperAdminOnly` authorization policies**, and the `SuperAdmin` bootstrap silently no-ops if `SuperAdmin:Email`/`Password` aren't configured (logs a warning, doesn't fail startup). If any admin-facing feature is planned, there is currently no way to reach it even after creating a SuperAdmin, since no controller checks these roles yet.
- **Redis is registered but entirely unused.** Either it's intended for a near-future feature (e.g. caching, distributed rate limiting) and can be left as-is, or it's currently dead infrastructure worth removing until there's a concrete consumer — worth a deliberate call rather than leaving it ambiguous.
- **The mobile app's `AuthInterceptor` already assumes a specific refresh-token request/response shape** (`{ "refreshToken": ... }` in, `{ accessToken, refreshToken }` out under the `data` envelope key) **before any auth feature or its own models exist to formalize that contract.** This happens to match the backend exactly today (verified above), but it's currently "tribal knowledge" encoded only inside `auth_interceptor.dart` rather than in a model/DTO either side can point to — worth keeping in sync consciously as the Auth feature gets built, rather than by coincidence.
