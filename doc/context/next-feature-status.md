This enum is **shared** between two unrelated concerns, per the comment at `InviteMethod.cs:3-4`: `EventGuest.InviteMethod` (how the user is inviting someone to their own event, set live) and `PersonOccasionHistory.InviteMethod` (how a person invited the user in the past, logged retroactively).

### Transitions — all in `EventGuestService.cs`

| Action | Endpoint | Effect on `Status`/`InviteMethod`/`InvitedAt` | Idempotency |
|---|---|---|---|
| Add to event (single or bulk) | `POST /` or `POST /by-group/{groupId}` | New `EventGuest` row created with `Status = NotInvited`, `InviteMethod = null`, `InvitedAt = null` (`EventGuestService.cs:298-303`) | Already-present persons are silently skipped, not duplicated — `AddGuestsAsync` diffs against existing `PersonId`s first (`EventGuestService.cs:288-306`); result DTO reports `AlreadyPresentCount` |
| Mark invited | `POST /{guestId}/invite` | `Status = Invited`; `InviteMethod = dto.InviteMethod`; `InvitedAt = UtcNow` (`EventGuestService.cs:212-219`) | **Idempotent upsert, not a guarded transition** — re-inviting an already-`Invited` guest just overwrites the method/timestamp (comment at `EventGuestService.cs:212-214`: "the simplest and most forgiving behavior for a personal tool") |
| Mark skipped | `POST /{guestId}/skip` | `Status = Skipped`; `InviteMethod = null`; `InvitedAt = null` (`EventGuestService.cs:236-239`) | Unconditional — works from any prior status |
| Revert | `POST /{guestId}/revert` | `Status = NotInvited`; `InviteMethod = null`; `InvitedAt = null` (`EventGuestService.cs:259-262`) | No-op if already `NotInvited` (comment at `EventGuestService.cs:258`) |
| Remove | `DELETE /{guestId}` | Row **hard-deleted** (`repo.Delete(guest)`, `EventGuestService.cs:281`) — not soft-deleted, unlike `Group`/`Person`/`Event` |

There is **no state-machine guard** anywhere (no "can't skip an already-invited guest" rule, etc.) — every transition endpoint unconditionally sets the target state regardless of the guest's current status. The only validation is that the guest row exists (`EventGuest.NotFound`).

## 4. Reciprocity computation ("who hasn't invited you back")

### Data read

The core query lives in `PersonOccasionHistoryWithSpecs.ReciprocityCandidates(ownerUserId)` (`YourSpace.Repository/Specifications/PeopleSpecifications/PersonOccasionHistoryWithSpecs.cs:37-38`):

```csharp
public static PersonOccasionHistoryWithSpecs ReciprocityCandidates(string ownerUserId)
    => new(h => h.Person.OwnerUserId == ownerUserId && h.InvitedMe);
```

It selects every `PersonOccasionHistory` row (unpaginated) where `InvitedMe == true`, scoped to the caller's own `Person` records. This spec is consumed in two different places for two different purposes:

1. **`PersonService`** — `GetReciprocityPersonIdsAsync` (`PersonService.cs:178-183`) projects the result to a `HashSet<int>` of `PersonId`s and sets `PersonProfileDto.HasReciprocityHistory = reciprocityPersonIds.Contains(p.Id)` on every row of `GET /api/v1/Persons` (`PersonService.cs:55-62`). `PersonService.GetDetailsAsync`/`UpdateAsync` instead load *all* history for that one person (`PersonOccasionHistoryWithSpecs.ForPerson`) and set `HasReciprocityHistory = history.Any(h => h.InvitedMe)` (`PersonService.cs:40-44`, `144-146`) — same boolean, different query shape depending on context (list vs. single).

2. **`EventGuestService.GetReciprocitySuggestionsAsync`** (`EventGuestService.cs:111-157`) — the actual "who hasn't invited you back for *this* event" endpoint:
   - Confirms the event exists for the caller (`EventGuest.EventNotFound` if not).
   - Loads `ReciprocityCandidates(ownerUserId)`, projects to distinct `PersonId`s.
   - Loads every existing `EventGuest` row for this event and excludes any candidate `PersonId` already added as a guest (`EventGuestService.cs:123-127`) — so a person already on the guest list, invited or not, never appears as a "suggestion".
   - If zero candidates remain, returns an empty paginated result immediately (`EventGuestService.cs:129-133`).
   - Otherwise loads the actual `Person` rows via `PersonWithSpecs(ownerUserId, candidateIds, groupId)` (optional `groupId` filter), **paginates in memory** (`OrderBy(p => p.Name).Skip(...).Take(...)`, comment at `EventGuestService.cs:138-140` explains why: "small candidate set at personal-event scale... avoids adding a paginated overload... for a rarely-large result set"), and maps to `PersonProfileDto` with `HasReciprocityHistory` force-set to `true` (`EventGuestService.cs:145-149`).

### Response shape

`GET /api/v1/events/{eventId}/guests/reciprocity-suggestions` returns `ServiceResult<PaginatedResultDto<PersonProfileDto>>` — the exact same `PersonProfileDto` shape used by the People list endpoint (Section 2), not a dedicated suggestion DTO. Every item's `HasReciprocityHistory` is `true` by construction.

### ⚠️ Verified gap: the `ReciprocitySuggestionsEnabled` toggle is not enforced

`UserSettings.ReciprocitySuggestionsEnabled` (`YourSpace.Data/Entities/UserSettings.cs:10`) exists as a per-user boolean, readable/writable via `GET`/`PUT /api/v1/UserSettings`, and defaults to `false` for a new user (`UserSettingsService.cs:45`). However, grepping the entire solution for `ReciprocitySuggestionsEnabled` shows it is referenced **only** inside `UserSettingsService`/`UserSettingsController`/its DTOs/tests/migrations/mock seed data. `EventGuestService.GetReciprocitySuggestionsAsync` (the method above) **never reads `UserSettings` at all** — the endpoint computes and returns suggestions unconditionally regardless of this flag's value. If the intent is for the flag to gate this endpoint (its name strongly suggests that), that wiring does not exist yet in the current code.

## 5. Pagination, filtering, sorting on list endpoints

### Pagination — shared across every list endpoint

`PaginationSpecification` (`YourSpace.Repository/Specifications/Paginated/PaginationSpecification.cs`), bound via `[FromQuery]`:

```csharp
public int PageIndex { get; set; } = 1;
public int PageSize { get; set; }   // default 10, hard-capped at 50 (MaxPageSize) — values above 50 are silently clamped, not rejected
```

Every list service method issues two queries: an unpaginated `CountWithSpecAsync` (for `TotalItems`) and a paginated `ListAllWithSpecAsync` (`Skip = PageSize * (PageIndex - 1)`, `Take = PageSize`) — e.g. `GroupService.GetAllAsync` (`GroupService.cs:41-54`). `PaginatedResultDto<T>` (`YourSpace.Services/Helper/PaginatedResultDto.cs`) wraps the page: `Items`, `PageIndex`, `PageSize`, `TotalItems`, `TotalPages` (`TotalPages = Ceiling(TotalItems / PageSize)`, computed per-call in each service, not on the DTO itself).

**Exception:** `GetReciprocitySuggestionsAsync` (Section 4) paginates in memory over an already-materialized candidate list rather than via `Skip`/`Take` in the specification — a deliberate exception documented in its own code comment (`EventGuestService.cs:138-140`).

## 6. Error response shape

Identical envelope to the Auth brief — every response, success or failure, is `ServiceResult`/`ServiceResult<T>` (`YourSpace.Services/Helper/ServiceResult.cs`), serialized camelCase:

```json
{
  "success": false,
  "message": "Group not found.",
  "errorCode": "Group.NotFound",
  "data": null,
  "statusCode": 404,
  "timestamp": "2026-07-28T12:34:56.789Z",
  "errors": null
}
```

Three distinct paths produce this envelope (same as Auth):
1. **FluentValidation failures** → HTTP **422**, `errorCode: "Validation.Failed"`, `errors` populated as `{ "FieldName": ["message1", ...] }`, via the same `InvalidModelStateResponseFactory` (`Program.cs:29-38`).
2. **Guard-clause failures inside the service** → the specific `ServiceResult` factory with its own status code and stable `errorCode` (table below).
3. **Unhandled exceptions** → `ExceptionMiddleware.cs` (500 in Production with a generic message, full exception detail only in Development).
